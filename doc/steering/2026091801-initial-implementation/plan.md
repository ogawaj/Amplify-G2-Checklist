# CheckList 初期実装 計画

## 目的・スコープ

`doc/persistent/product-requirements.md` と `doc/persistent/functional-design.md` で定義した CheckList を、テンプレート状態から初期リリース相当まで実装する。

**対象:** 機能F-01〜F-15、画面S-01〜S-09、受け入れ条件AC-01〜AC-11のすべて。

**スコープ外:** 永続ドキュメントの「スコープ外（初期リリース）」に挙げた項目（複数アカウント共有、外出履歴、ドラッグ並べ替え、未チェックのみ表示、外部共有・印刷、CSV入出力のスマートフォン対応、カテゴリ・タグの一括削除、通知、オフライン利用）。

**前提:**

- Lambda関数は作らない。一括処理はフロントエンドのService層に置く（functional-design.md §一括処理）
- `shared/` は使用しない。共有定義は `src/app/` 配下に置く
- レスポンシブ対応（AC-07）は各画面の実装に含める
- モックは `doc/persistent/mockup/` を参照する。配色・コンポーネントの確定仕様ではない

## タスク一覧

### task-01-cleanup-template

- **概要**: テンプレートのサンプルコードを削除し、CheckListの実装に必要な土台だけを残す。
  `amplify/data/resource.ts` から `Todo` / `DailyAccessSummary` モデルと `cklSayHello` / `cklAggregateAccess` のカスタムクエリを削除する。
  `amplify/functions/` 配下（`ckl-say-hello` / `ckl-aggregate-access` / `functions/common/`）と `amplify/backend.ts` の関数登録・環境変数注入ループを削除する。`amplify/common/` は `backend.ts` が環境名の解決に用いるため残す。
  `shared/`（`enums/batch-operation.ts` / `utils/enum-utils.ts`）と `amplify/tsconfig.json` の `@shared/*` パスエイリアスを削除する。
  フロントエンドの `hooks/use-todo.ts` `hooks/use-access-summary.ts` `services/todo-service.ts` `services/access-summary-service.ts` `repositories/todo-repository.ts` `repositories/access-summary-repository.ts` を削除し、これらを参照する `components/home/index.tsx` を最小構成に置き換える。
  環境変数まわり（`enums/env-variable-*.ts` `models/env-variable.ts` `services/env-variable-service.ts` `hooks/use-env-variable.ts`）とパスワードポリシー・タグ付与は残す。
  完了時点で `npm run lint` と `tsc --noEmit` が通り、削除漏れの参照がない状態にする。
- **依存**: なし

### task-02-checklist-implementation

- **概要**: CheckListの全機能を実装する。フェーズに分けて進め、各フェーズの完了時点でビルドが通る状態を保つ。

  **フェーズA: データモデルと共通層**
  `amplify/data/resource.ts` に `CheckList` / `Category` / `Tag` / `Item` の4モデルを定義する（functional-design.md §テーブル定義）。`checkListId` にセカンダリインデックスを設定し、全モデルに `allow.owner()` を適用する。
  `src/app/enums/` に上限値（日数1〜60・数量1〜999・CSV500行）・一括処理の同時実行数・CSV列定義、`src/app/models/` にCSV行と一括処理の結果型を追加する。
  `src/app/repositories/` に4モデルのRepositoryを作成する（データ変換は行わない）。同時実行数を制限した並列実行のユーティリティをService層に用意する。

  **フェーズB: 認証（S-01〜S-03、F-12、AC-06）**
  `(public-page)` にサインイン・サインアップ・パスワード再設定を作成する。サインアップは確認コードによる本人確認、パスワード再設定は確認コードによる再設定とする。
  `(auth-page)` 配下を未認証時に `/sign-in` へリダイレクトし、ルート（`/`）は認証状態に応じて `/lists` または `/sign-in` へ振り分ける。サインアウトの導線を認証済みページのヘッダーに置く。

  **フェーズC: チェックリスト一覧（S-04、F-01・F-02、AC-01）**
  名称・日数・最終更新日時のみを表示し、持ち物の集計は行わない。新規作成（「未分類」カテゴリを併せて作成）・名称変更・複製・削除を実装する。
  複製はカテゴリ・タグ・持ち物・日数を引き継ぎ、チェック状態は未チェックとする。削除は配下を削除してから本体を削除する。いずれも並列実行ユーティリティを用い、進捗と完了を示す。削除は確認ダイアログを挟む。

  **フェーズD: チェックリスト詳細（S-05、F-06〜F-11、AC-03〜AC-05）**
  カテゴリ順に持ち物を表示し、行の右端のチェックボックスで準備状況を切り替える（楽観的更新）。
  タグフィルタは読み込み済みの持ち物に対するクライアント側の絞り込みとし、タグ未設定の持ち物は常に表示、0件になったカテゴリは見出しごと隠す。
  日数の入力（1〜60）と数量計算（1日あたり×日数）を実装し、計算結果と算出根拠を併記する。数量未設定には数量を表示しない。
  一括リセットはフィルタの適用状態に関わらず全持ち物を対象とし、チェック済みのみ更新する。確認ダイアログを挟む。
  ヘッダーに進捗（準備済み件数／総件数）を表示する。「⋯」メニューから持ち物編集・カテゴリ管理・タグ管理へ遷移させる。

  **フェーズE: 持ち物編集（S-06、F-03・F-09・F-15、AC-02・AC-08）**
  一覧の各行を直接入力にする。名称・数量をその場で編集し、フォーカスが外れた時点で保存する。タグはチップのタップで付け外しする。
  各カテゴリの末尾に入力待ちの行を置き、名称を確定した時点で追加する。空のまま確定した場合は変更を取り消す。
  削除対象の選択は行の左端に丸型のチェックボックスを置き、準備状況のチェックと区別する。選択件数バー・全選択・一括削除を実装し、タグフィルタ適用中は表示中の持ち物のみを選択対象とする。一括削除は選択件数を示す確認ダイアログを挟む。

  **フェーズF: カテゴリ管理・タグ管理（S-07・S-08、F-04・F-05、AC-10・AC-11）**
  どちらも一覧の各行を直接入力とし、末尾の追加行から新規作成する。件数は表示しない。
  カテゴリは▲▼ボタンで表示順を変更し、詳細画面に反映する。名称は同一チェックリスト内で重複を許さない。
  削除は、カテゴリは所属する持ち物が、タグは付与された持ち物が1件でもあれば拒否する。判定は持ち物一覧から行い、拒否時は理由と持ち物編集画面への導線を示す。紐付きがない場合のみ確認ダイアログを挟んで削除する。

  **フェーズG: CSV入出力（S-09、F-13・F-14、AC-09）**
  エクスポートは読み込み済みの持ち物からService層で文字列を生成し、BOM付きUTF-8・CRLFでダウンロードする。列は `識別子,カテゴリ,持ち物名,1日あたり,タグ`、タグはセミコロン区切りとする。
  インポートは同期方式のみとする。識別子で既存と突き合わせて新規・更新・変更なし・削除・失敗に分類し、確認画面で件数と内容、取り込めない行の行番号と理由を示してから実行する。
  形式不備で除外された行に対応する既存の持ち物は削除しない。更新された持ち物のチェック状態は維持し、新規登録分は未チェックとする。カテゴリ名・タグ名が未登録なら併せて作成する。
  識別子の列を編集しないよう注意を示す。この画面への導線はデスクトップ幅でのみ表示する。

  **全フェーズ共通**
  レスポンシブ対応（AC-07）は各画面の実装時に行い、後追いで当てない。破壊的操作（削除・一括削除・一括リセット・CSV取り込み）は確認ダイアログを挟む。
- **依存**: task-01

## 推奨実行順序

| 順  | タスク                        | 着手条件     | 並列実行可能性 |
| --- | ----------------------------- | ------------ | -------------- |
| 1   | task-01-cleanup-template      | —            | —              |
| 2   | task-02-checklist-implementation | task-01 完了 | —              |

**順序の理由:**

- task-01 を先に置くのは、サンプルコードを残したままモデルを追加すると `amplify/data/resource.ts` が二重管理になり、削除時の影響範囲が広がるため
- task-02 内はフェーズA→Gの順に進める。フェーズAの共通層を後続すべてが使い、フェーズD以降は画面の入れ子（詳細 → 持ち物編集 → 管理画面）に沿って前のフェーズの行コンポーネントとService層を再利用する
