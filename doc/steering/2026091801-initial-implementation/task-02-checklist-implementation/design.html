Design

task-02: CheckList 全機能の実装

実装アプローチ

  • レイヤーを下から積む。各フェーズで Repository → Service → Hook → Component の順に実装する。Hook から Repository を直接呼ばない
  • 詳細データは1回だけ読む。チェックリストの持ち物・カテゴリ・タグを詳細画面で一括取得し、絞り込み・数量計算・進捗集計・削除可否判定はすべてクライアント側の Service で行う。操作のたびに再取得しない
  • 直接入力を1箇所に集約する。フォーカス喪失時の保存・楽観的更新・失敗時の巻き戻しを共通コンポーネントに実装し、持ち物・カテゴリ・タグで共用する
  • 一括処理を1つのユーティリティに集約する。同時実行数を制限した並列実行を Service に置き、リセット・一括削除・複製・チェックリスト削除・CSV取り込みで共用する
  • 確認ダイアログを共通化する。破壊的操作の確認のみ Dialog を使い、件数と取り消せない旨を渡す共通コンポーネントにする

設計判断

詳細データを S-05〜S-08 で共有する

タグの削除可否（AC-11）とカテゴリの削除可否（AC-10）の判定には、チェックリスト内の持ち物一覧が必要になる。 件数を画面に出さない仕様のため集計APIは持たず、詳細画面で取得済みの持ち物配列を管理画面でも使う。 S-05〜S-08 は /lists/[listId] 配下に置き、読み込みを担う Hook を共有する。

一括処理の失敗を握りつぶさない

一括処理はロールバックしない（functional-design.md §一括処理）。成功件数と失敗件数を戻り値に含め、 画面で結果を提示する。処理中は同じ操作を再実行できないようにする。

認証ガードとヘッダーをレイアウトに置く

(auth-page)/layout.tsx に未認証時のリダイレクトと共通ヘッダー（アプリ名・環境バッジ・サインアウト）を集約する。 ヘッダーは task-01 で残した components/home/index.tsx の実装を転用し、components/common/ へ移す。

一括処理をクライアント側で行う（DB規約との関係）

coding-standards-db.md §クエリの効率は「1件ずつのループ呼び出しを避け、カスタムmutationへの集約を検討する」とするが、 検討のうえ採用しない（functional-design.md §一括処理）。カスタムmutationでもAppSync経由の書き込みは1件ずつで回数が減らず、150件規模ではLambdaの起動時間の分だけ不利なため。 architecture.md §性能・バッチ処理に従い、行ごとの失敗は記録して続行し、順序依存のある段階（複製のチェックリスト作成 → カテゴリ・タグ作成 → 持ち物作成、削除の持ち物 → タグ・カテゴリ → 本体）は段階間を直列にする。

入力値の範囲と名称の一意性はフロントで検証する

日数（1〜60）・数量（1〜999）・CSV行数（500）・カテゴリ名とタグ名の一意性は、フロントの Service で検証する。 architecture-db.md はサーバー側で強制されない旨を述べるが、api-design.md §想定脅威モデルのとおり直接のAPI呼び出しは想定外とし、サーバー側での強制は行わない。

進捗の母集団

ヘッダーの進捗とカテゴリ見出しの件数は、タグ絞り込み後に表示されている持ち物を母集団とする（モック S-05 のとおり）。一括リセットの対象（絞り込みに関わらず全件）とは母集団が異なるのは意図した仕様である。

Repository の実装規約

coding-standards-db.md / architecture-db.md に従う。generateClient<Schema>({ authMode: "userPool" }) は Repository のモジュール内でのみ生成する。 一覧取得は checkListId のセカンダリインデックスのクエリ関数で行い（list の filter は使わない）、nextToken を辿って全件を返す。 型付きクライアントが返す errors は加工せずに投げる。持ち物の数量を消すときは null を送る（undefined では更新されない）。

配列ユーティリティの置き場所

coding-standards.md §DRY は配列の汎用処理を shared/utils/array-utils.ts に置くとするが、本プロダクトはバックエンドのコードを持たず shared/ を使わない設計のため、 フロント専用の src/app/utils/array-utils.ts に置く。lodash は使わない点は規約に従う。

データ構造の変更

GraphQL のモデル定義は functional-design.md §テーブル定義を正とする（CheckList / Category / Tag / Item の4モデル）。 本タスクで新たに定義するフロントエンド側の型は次のとおり。

型内容
CheckList / Category / Tag / ItemSchema["Item"]["type"] のようにスキーマから派生させる。フィールドを手書きで再定義しない
CsvRow識別子・カテゴリ名・持ち物名・1日あたり・タグ名配列
CsvParseResult正常行の配列と、行番号・理由を持つ失敗行の配列
ImportDiff新規・更新・変更なし・削除・失敗の各配列
BulkResult成功件数・失敗件数・失敗の理由
