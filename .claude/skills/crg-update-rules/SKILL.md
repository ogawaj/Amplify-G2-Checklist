# .claude ルール反映

ユーザーから受けた指摘・課題を `.claude/rules/` に反映する作業を、**重複なく・既存ルールを生かす形で** 実施します。

## 前提となる思想

規約違反が起きた時、原因は通常 2 つに分かれます：

1. **ルールが無かった** → 新規ルール追加の対象
2. **ルールはあったが適用されなかった** → ルール強化ではなく **適用の問題**。再掲は冗長

多くの場合は 2 です。安易にチェックリスト化して既存ルールを言い換えると、ファイルが膨れて読まれにくくなり、結局守られない悪循環に陥ります。

**本当に新しい指針だけを最小限の表現で追記する** ことを徹底します。

## 手順

以下の手順を **厳密に** 順番通り実行してください。

### Step 0: 反映対象の指摘の収集

会話の履歴から、ルール化すべき指摘を抽出します。

抽出対象の典型例：

- コーディング規約違反の指摘（命名規則 / 配置 / 型定義方法 等）
- 用語揺らぎの指摘（UI 表示文字列の表記統一 等）
- 依存管理に関する指摘（未使用ライブラリ / 重複定義 等）
- アーキテクチャ違反の指摘（レイヤー越境 等）
- ドキュメント不整合の指摘

各指摘について以下を整理：

- **何が問題だったか**
- **何が正解だったか**
- **どの場面で発生する間違いか**（再発防止のため）

### Step 1: 既存ルールの全文読み込み

`.claude/rules/` 配下の全 `.md` ファイルを読み込みます：

- `architecture.md` — アーキテクチャ・レイヤー構成・配置ルール（汎用）
- `architecture-db.md` — DB 固有のアーキテクチャ規約（Amplify Data + DynamoDB）
- `coding-standards.md` — 命名規則・データモデル・ドメイン定数・文言・YAGNI 等（汎用）
- `coding-standards-db.md` — DB 固有のコーディング規約（型付きクライアント優先・エラーの扱い・クエリの効率）
- `api-design.md` — GraphQL / REST API 設計
- `document.md` — ドキュメント整備ルール

ルールの **既存構造（セクション見出し・既存表）** を把握しておく。後段の重複チェックで使う。

### Step 2: 既存ルールとの突合（重複チェック・最重要）

Step 0 で集めた各指摘について、**既存ルールに同等の規定が既に書かれているかを 1 件ずつ確認** します。

確認の仕方：

- ルールファイル内を grep / Read で検索
- 「同じ意味のことが書かれているか」を判定（言い回しが違っても本質が同じなら重複）

判定結果に応じて分類：

| 分類                     | 判定                                       | 対応                                                   |
| ------------------------ | ------------------------------------------ | ------------------------------------------------------ |
| 完全に既存ルールでカバー | 同じ趣旨が既に明記されている               | **追加しない**。ユーザーに「既存ルールで覆える」と報告 |
| 既存ルールの応用例       | 既存ルールから論理的に導けるが具体例がない | 既存セクションに **1 行の具体例** を追加               |
| 完全に新規               | 既存ルールに該当無し                       | 新セクション or 既存表への新行で追加                   |

**重複疑いは「追加しない」側に倒す**。冗長性のリスクを優先。

### Step 3: 追記方針の決定

Step 2 で「追加対象」と判定したものについて、書き方を決めます：

- **既存表への 1 行追加** で済むか（命名規則表など）
- **既存セクション末尾に 1〜2 行追加** で済むか
- **新セクション** が必要か（表で整理できるなら表形式）

優先順位は **影響最小**：表 1 行 > 既存セクション補強 > 新セクション。

新セクションを作る判断基準：

- 完全に新しい関心領域である（例: 依存管理、UI 用語統一）
- 表形式で整理した方がスキャンしやすい
- 既存セクションのいずれにも自然に収まらない

### Step 4: ユーザーへの追記案提示

追記する内容と「**重複していないこと**」「**既存ルールでカバー済みのものは除外したこと**」を明示してユーザーに提示する。

報告フォーマット例：

```
## 追記する内容（新規価値あり）

1. <ファイル>:<行範囲> — <追加項目>
2. <新規セクション> — <概要>

## 既存ルールで覆えるため追加しないもの

- <指摘 A> → <既存ルール参照>
- <指摘 B> → <既存ルール参照>
```

ユーザーの承認を待つ。フィードバックがあれば修正する。

### Step 5: 反映

承認された内容を `.claude/rules/` の該当ファイルに反映する。

- 既存表への追加: `Edit` で表行を追加
- 既存セクションへの追記: `Edit` で末尾に追加
- 新セクション: `Edit` で適切な位置に挿入

フォーマッタが自動整形する場合があるので、編集後に該当ファイルを読み直して整形結果を確認する。

### Step 6: 重複の最終チェック

反映後、改めて以下を確認：

- 追加した内容と既存ルールの間に重複がないか
- セクション間で類似内容が分散していないか
- ファイル全体の流れが自然か（読み手が混乱しないか）

問題があれば再修正する。

### Step 7: 完了報告

ユーザーに以下を報告：

- 反映したファイル一覧
- 追加した項目の要約
- 既存ルールで覆えるため追加しなかった指摘とその根拠
- コミット要否の確認（自動でコミットしない）

## ルール

- **既存ルールで覆える指摘は絶対に追加しない**（チェックリスト化のための再掲は冗長）
- **「適用怠り」が原因の場合はルール強化で解決しない** — 適用を促す仕組み（review エージェントの強化等）は別の問題
- **新セクション > 表 > 1 行追記** の順で影響を最小化する
- **本当に新しい価値のある指針だけを追加** — 「念のため書いておく」は禁止
- 反映後の重複チェックを必ず実施する
- 自動コミットしない（ユーザーが指示するまで待つ）

## アンチパターン

以下は典型的な失敗パターン：

### ❌ チェックリスト形式で既存ルールを言い換える

```markdown
## 新規追加時の自己レビュー

- [ ] ファイル名は kebab-case で役割サフィックス付きか ← 既存「命名規則」と重複
- [ ] データの形状型は `models/` 配下に置いたか ← 既存「データモデル」と重複
- [ ] 文字列リテラル直書きしていないか ← 既存「ドメイン定数」と重複
```

→ **既存ルールが守られなかったのは「チェックリストが無かった」からではなく「適用しなかった」から**。再掲しても解決しない。

### ❌ 「規約違反が起きた = ルール追加」と短絡する

規約違反を見たら、まず **既存ルールでカバーされているか** を確認する。9 割は既存ルールで覆える。覆えるなら追加しない。

### ❌ 念のため・将来のため

「将来似た問題が起きるかも」「念のため書いておこう」で追加しない（YAGNI）。実際に起きてから追加する。
